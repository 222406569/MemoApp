这是一个个人小型项目的需求列表，帮我分析一下有哪些可以用于实现该项目的技术栈，以及各技术栈方案的利弊

这个备忘录适合做成常驻托盘的 Windows 桌面程序，数据库用 SQLite。语言按你已经会的来选：会 Web 用 Tauri 2 + Vue 或 React，会 C# 且只在这台 Windows 上用就用 .NET 8 WPF。

四套方案的对照放在 工作备忘录技术栈，可以在对话旁边打开，点方案名称切换利弊。这是一块独立的可视化面板，方便横着比较，不用在长文里来回翻。

需求把形态定死了
事项、客户、进度状态都在本机，SQLite 已经写进需求。查找、批量改字段、多字段排序、联想输入，都是一张可编辑的表格。提醒要弹出系统通知，还要按「当前时间往前或往后几小时」判断，所以进程得在窗口关掉之后继续跑。导出先做 CSV 和 xlsx，以后再加一个把事项写入公司工单的接口。

因此浏览器里开一个本地页面不够用：页面一关，提醒就停了。下面四套都是带托盘的桌面程序。

四套方案
Tauri 2 + Vue 或 React。 界面用网页技术做筛选、勾选和联想，SQLite 与系统通知用 Tauri 插件，业务仍写 TypeScript。安装包和内存适合整天挂着。代价是要装 Rust 工具链，打包和跨层调试比纯网页多一步。已经会前端时，这是最均衡的一版。

.NET 8 WPF + Microsoft.Data.Sqlite。 DataGrid 做单条修改和「勾选记录、勾选字段、填新值」最顺，Windows 通知和托盘是系统能力，Excel 用 ClosedXML。代价是界面只服务 Windows，筛选器和联想框要自己组。会 C#、而且就这台电脑用，维护成本最低。

Electron + Vue 或 React + better-sqlite3。 功能和 Tauri 方案几乎一样，资料也多，主进程可以在窗口隐藏后继续扫提醒。代价是自带一套浏览器内核，一个备忘录整天开着偏重。只有你已经熟 Electron 时才值得选。

Python 3 + PySide6 + 标准库 sqlite3。 建表、增删改查、CSV、openpyxl 写 xlsx 都很快，文本规则（等于、包含、开头、结尾）用 Python 写最直白。代价是打成 exe 后体积和启动一般，系统通知要另接库，界面也粗一些。适合先做出能用的一版，业务逻辑不要写死在按钮里。

从零开始、又没有偏好时，优先 Tauri：表格和筛选用前端组件更快，体积又适合常驻。

语言可以后换，这几块从第一版就分开：事项上的客户和状态存编号，名称放在客户表和状态表里，并各带一个排序优先级。这样改名会同步到事项，输入联想也只能选出已维护的名称。筛选默认条件、多字段排序（含空值在前或在后）、提醒规则各自存配置。附件放磁盘，库里只记路径。导出做成适配器，CSV 和 xlsx 是前两个实现，以后写工单就是同一个接口的另一种实现。

有三处建议在动手前定一下：查找里的「用户名」在数据模型里对应的是客户名称；「xsl」按 xlsx 来做；删除某个进度状态时「连同该状态的事项一起删」不可恢复，个人工具里更稳妥的做法是仍有事项引用时禁止删除。

采用Tauri2 + Vue，前端语言不用js，用ts

需求已更新：查找按客户名，删除状态时若仍有事项引用则禁止删除，导出格式是 xlsx。接下来按 Tauri 2、Vue 3 和 TypeScript 定实现计划。

用 Tauri 2、Vue 3 和 TypeScript 做本机单人工作备忘录：SQLite 存事项、客户和状态，界面负责表格维护、排序、提醒和导出，Rust 只保留托盘和插件注册。
